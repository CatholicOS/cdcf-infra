# Martyrology — auth handoff

Generated by `setup-zitadel.sh --provision-martyrology` + `setup-openfga.sh --create-martyrology-store` against the prod umbrella infra.

Consumer repo: [`CatholicOS/martyrology-api`](https://github.com/CatholicOS/martyrology-api).

This handoff records only the **non-secret** values needed to point `martyrology-api` at the shared infra. The OIDC **client secret** is emitted ONCE at provisioning time and is delivered out-of-band — see the two warnings immediately below, which are the two ways this provisioning goes wrong in practice.

---

## ⚠ Warning 1 — the client secret is printed once and is unrecoverable

`setup-zitadel.sh --provision-martyrology` creates a confidential API app (`API_AUTH_METHOD_TYPE_BASIC`) and prints `MARTYROLOGY_ZITADEL_CLIENT_SECRET` **exactly once**, in the output of the run that creates it. Zitadel's `ListApplications` API does not return secrets, so re-running the provisioner against an existing app cannot recover it (see `auth/README.md` → "First-time bring-up").

**Write the secret into `/etc/martyrology/api.env` on the VPS during the provisioning run — not afterwards, not "later today".** If the shell scrolls away or the session drops before you paste it, the only remedy is to rotate:

> Zitadel console → `Martyrology` Org → Projects → `MartyrologyAPI` → Apps → `MartyrologyAPI Backend` → Regenerate Client Secret

Recommended: run the provisioner in a session where you already have `/etc/martyrology/api.env` open in an editor on the VPS.

## ⚠ Warning 2 — until the env is filled in, the API is up but unauthenticated

`martyrology-api` computes its auth posture from the env, in `src/martyrology_api/config.py`:

```python
@property
def auth_enabled(self) -> bool:
    return bool(self.zitadel_issuer)

@property
def authz_enabled(self) -> bool:
    return bool(self.openfga_api_url and self.openfga_store_id)
```

With `MARTYROLOGY_ZITADEL_ISSUER` empty, **`auth_enabled` is `False`** — and likewise `authz_enabled` is `False` while the OpenFGA vars are empty. The service still starts and reports healthy. It does **not** fail closed on the write path: the curator surfaces (`PUT`/`PATCH`/`DELETE`) are reachable **unauthenticated** in that state.

The copyrighted texts stay redacted for anonymous callers regardless of this setting, so the read-side licensing exposure is not the risk here — **the write surfaces are**. Do not expose the deployment publicly with a partially-filled env. Fill all six `MARTYROLOGY_*` vars in the same maintenance window, or keep the write surfaces firewalled until you do.

### Why no roles

`martyrology-api` contains **no Zitadel role check and no scope check anywhere**. Zitadel supplies identity only: the API POSTs the bearer token to `$issuer/oauth/v2/introspect` (HTTP Basic with `client_id`/`client_secret` — which is why this app needs `_BASIC` rather than LitCal's `PRIVATE_KEY_JWT`), takes the `sub` claim, and hands `user:<sub>` to OpenFGA. Every authorization decision is an OpenFGA `Check`.

Adding project roles "for symmetry" with the LitCal and CDCF Website projects would put claims in the token that nothing reads — an authorization signal that looks load-bearing and isn't. If the API ever grows a role check, add the roles at that point.

### Model shape

```
type user

type governance_body
  define admin:  [user]
  define editor: [user] or admin
  define reader: [user] or editor

type edition
  define governed_by:    [governance_body]
  define can_admin:      admin  from governed_by
  define can_edit:       editor from governed_by
  define can_read_texts: reader from governed_by
```

Permissions are granted on the **governing body**, never on an individual edition, and are inherited by every edition that body governs (`tupleToUserset` — "X from governed_by"). Grant someone `editor` on `governance_body:cei` once and they can edit every Italian edition the CEI published, including ones added later.

`reader ⊂ editor ⊂ admin`: reader reads (including the copyrighted texts), editor additionally edits content, admin additionally handles edition lifecycle and is the intended role-granting authority.

The API checks `can_read_texts`, `can_edit`, and `can_admin` on `edition:<edition_id>` objects — exactly as it does today. **No `martyrology-api` code change is required**: the governance indirection resolves entirely inside the model.

### Governance bodies

| Edition ID | Scope | Nature | Governance body |
| --- | --- | --- | --- |
| `martyrologium_romanum_1584` | universal | `editio_typica` | `editio_typica` |
| `martyrologium_romanum_1749` | universal | `editio_typica_recognita` | `editio_typica` |
| `martyrologium_romanum_1914` | universal | `editio_typica_recognita` | `editio_typica` |
| `martyrologium_romanum_2001` | universal | `editio_typica` | `editio_typica` |
| `martyrologium_romanum_2004` | universal | `editio_typica_altera` | `editio_typica` |
| `martyrologium_romanum_2004_it_IT` | IT | `editio_vernacula` | `cei` |
| `martyrologium_romanum_1914_en_unofficial` | universal | `translatio` | `unassigned_en_translatio` |
| `martyrologium_romanum_2004_en_unofficial` | universal | `translatio` | `unassigned_en_translatio` |

- `editio_typica` — the Dicastery for Divine Worship and the Discipline of the Sacraments. Governs all Latin editions.
- `cei` — Conferenza Episcopale Italiana. Governs the Italian editions the CEI published.

### ⚠ `unassigned_en_translatio` is an intentional empty placeholder

The two English editions carry **`scope: universal`** in `clbdr/data/editions.json` — because they translate a universal edition, not because a universal authority published them. **Any rule that derives governance from `scope` would silently file them under the Dicastery, granting Dicastery readers/editors/admins rights over texts the Dicastery does not govern.**

They were published by a **publishing house**, not by the USCCB, so they also fall outside the Bishops' Conference model — there is no existing body they belong to.

`unassigned_en_translatio` is therefore created with **no members**. Every `can_*` check against these two editions resolves to `false`: they **fail closed** until their governance is decided. This is deliberate — a placeholder, not an oversight. Do not "fix" it by pointing these editions at `editio_typica`. Resolving it means either identifying the real governing body and re-pointing the `governed_by` tuple, or deciding these editions are administered directly by the project and granting named individuals on this body.

## One-time tuple seeding

`setup-openfga.sh` uploads the **model** but **never writes tuples**. The `governed_by` tuples are structural data the model is useless without — with no tuples, every check returns `false` for everyone, including admins. Run these once, on the VPS, after `--create-martyrology-store`.

These use the same invocation style as the script's `fga()` helper (`curl` against the internal listener, Bearer preshared key). Export the two values first:

```bash
export OPENFGA_INTERNAL_URL=http://127.0.0.1:8081
export OPENFGA_PRESHARED_KEY=<out-of-band>
export MARTYROLOGY_STORE_ID=<store ID from the --create-martyrology-store output>
```

### Seed `governed_by` (all 8 editions, one request)

```bash
curl -sS -X POST "${OPENFGA_INTERNAL_URL}/stores/${MARTYROLOGY_STORE_ID}/write" \
  -H "Authorization: Bearer ${OPENFGA_PRESHARED_KEY}" \
  -H "Content-Type: application/json" \
  -d '{
    "writes": {
      "tuple_keys": [
        {"user":"governance_body:editio_typica","relation":"governed_by","object":"edition:martyrologium_romanum_1584"},
        {"user":"governance_body:editio_typica","relation":"governed_by","object":"edition:martyrologium_romanum_1749"},
        {"user":"governance_body:editio_typica","relation":"governed_by","object":"edition:martyrologium_romanum_1914"},
        {"user":"governance_body:editio_typica","relation":"governed_by","object":"edition:martyrologium_romanum_2001"},
        {"user":"governance_body:editio_typica","relation":"governed_by","object":"edition:martyrologium_romanum_2004"},
        {"user":"governance_body:cei","relation":"governed_by","object":"edition:martyrologium_romanum_2004_it_IT"},
        {"user":"governance_body:unassigned_en_translatio","relation":"governed_by","object":"edition:martyrologium_romanum_1914_en_unofficial"},
        {"user":"governance_body:unassigned_en_translatio","relation":"governed_by","object":"edition:martyrologium_romanum_2004_en_unofficial"}
      ]
    }
  }'
```

A successful write returns `{}`. Re-running is **not** idempotent — OpenFGA rejects a duplicate tuple with `write_failed_due_to_invalid_input`. That is safe (nothing is corrupted); it just means the tuples are already there.

### Verify

```bash
curl -sS -X POST "${OPENFGA_INTERNAL_URL}/stores/${MARTYROLOGY_STORE_ID}/read" \
  -H "Authorization: Bearer ${OPENFGA_PRESHARED_KEY}" \
  -H "Content-Type: application/json" \
  -d '{"tuple_key":{"relation":"governed_by"}}' | jq '.tuples | length'   # → 8
```

### Grant a person a role on a body

Zitadel's `sub` claim is the user identifier — an opaque numeric string, visible in the Zitadel console under `Martyrology` Org → Users → the user → ID. Grant on the **body**, never on an edition:

```bash
# Give a Dicastery curator edit rights over every Latin edition:
curl -sS -X POST "${OPENFGA_INTERNAL_URL}/stores/${MARTYROLOGY_STORE_ID}/write" \
  -H "Authorization: Bearer ${OPENFGA_PRESHARED_KEY}" \
  -H "Content-Type: application/json" \
  -d '{
    "writes": {
      "tuple_keys": [
        {"user":"user:381902445667123201","relation":"editor","object":"governance_body:editio_typica"}
      ]
    }
  }'
```

Swap `"relation"` for `reader` or `admin`, and the object for `governance_body:cei`, as needed. Revoke by sending the identical tuple under `"deletes"` instead of `"writes"`.

Confirm it resolved through the indirection:

```bash
curl -sS -X POST "${OPENFGA_INTERNAL_URL}/stores/${MARTYROLOGY_STORE_ID}/check" \
  -H "Authorization: Bearer ${OPENFGA_PRESHARED_KEY}" \
  -H "Content-Type: application/json" \
  -d '{"tuple_key":{"user":"user:381902445667123201","relation":"can_edit","object":"edition:martyrologium_romanum_1749"}}'
# → {"allowed":true}
```

```bash
MARTYROLOGY_ZITADEL_CLIENT_ID=<populated on first run>
MARTYROLOGY_ZITADEL_CLIENT_SECRET=<out-of-band — one-time emit, see Warning 1>

MARTYROLOGY_OPENFGA_API_URL=https://authz.catholicdigitalcommons.org
MARTYROLOGY_OPENFGA_STORE_ID=<populated on first run>
MARTYROLOGY_OPENFGA_MODEL_ID=<populated on first run>
```

All six must be set together — see Warning 2.

### What the API checks

The API issues `POST /stores/<id>/check` with `{"tuple_key": {"user": "user:<zitadel sub>", "relation": <rel>, "object": "edition:<edition_id>"}}`. Exactly three relations are ever checked:

| Relation | What it gates |
| --- | --- |
| `can_read_texts` | Reading the copyrighted texts of a restricted edition (anonymous callers get redacted output) |
| `can_edit` | `PUT` / `PATCH` / `DELETE` on elogia, and on month/day data |
| `can_admin` | `PUT /{edition_id}` (create edition) and `PATCH /{edition_id}` (edition metadata) |

### The write split is by resource, not by HTTP verb — confirmed intended

`routers/curation.py` divides content from container rather than dividing verbs:

- **`can_edit` — content.** `PUT`, `PATCH` and `DELETE` on elogia, plus month/day
  data. An editor may delete an individual elogium.
- **`can_admin` — the container.** `PUT /{edition_id}` (create an edition) and
  `PATCH /{edition_id}` (edition metadata).

An earlier reading of the policy expected a verb-based split (editor = `PATCH`,
admin = `PUT`/`PATCH`/`DELETE`). The owner confirmed the resource-based split is
what is wanted: an editor can delete an elogium, but not an entire edition.

That distinction is stronger than it looks, because **the API exposes no route
that deletes an edition at all** — there is no `DELETE /{edition_id}`. Edition
removal is not an authorization decision here; it is simply not reachable
through the API, and would have to be done in the data repository directly. So
`can_admin` is best read as "may create an edition and edit its metadata",
not as "may destroy one".

## What's NOT provisioned here (follow-ups)

- **Tuple seeding is manual.** `setup-openfga.sh` has no tuple-writing capability. Folding the `governed_by` seed into the shared script (e.g. an optional `auth/models/<Store>.tuples.json` applied idempotently after the model upload) is proposed as a follow-up, deliberately out of scope for the onboarding PR.
- **Governance for the English editions** — see the `unassigned_en_translatio` section above.
- **Human role grants** — no individual has any role on any body until someone runs the grant command above. Each curator signs in to Zitadel once so a `sub` exists, then gets a tuple.
